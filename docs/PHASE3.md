# Phase 3 — Editing depth

See [PLAN.md](PLAN.md#phase-3--editing-depth) for the whole phase and [USABILITY.md](USABILITY.md) for the decisions behind it. Phase 3 adds darktable's editing tools behind Lightroom-style controls. It starts with the groundwork they need: process versions, so that rendering changes never alter existing edits, and the Develop tool stack that the new tools join, with Crop as its first group.

## Part 1: Process versions, the tool stack, and Crop

**What it does.** Three things. Every edit now records which version of LightBench's rendering it uses (its **process version**), so later rendering changes never silently change an existing edit. Develop's right panel is now **one scrolling stack of tool groups** in workflow order with a **jump bar**. Its new first group is **Crop**: crop, straighten, rotate 90° and flip, on the photo and in the panel, Lightroom-style.

Owner's choices (2026-10-12):
1. **Process versions first.** Existing edits are version 1 (today's rendering); new edits get the current version; rendering code can branch on the version; the version is shown unobtrusively and an older edit offers **Update to current process**, which can be compared and undone through the history. Today there is one rendering, so this is the mechanism and its tests.
2. **The tool stack**, already decided after round 2: one scrolling stack, Crop & Lens first, then Basic; collapsible groups; a jump bar with icons and one-word labels (labels hide when narrow, the name shows on hover). Only groups with content exist (Crop, Basic); Curve, Colour, Detail and Effects slot in later. The on/off **eye** per group (an idea from LightCraft; LightBench's choice to include it) shows the photo without that group.
3. **Crop, Lightroom-style:** **R** opens it on the photo (an action in the shortcut registry, so it can be changed); drag corners or edges to resize, inside to move, outside to turn; the crop box stays level and the photo turns under it (Lightroom's way; LightCraft turns the box instead). Aspects Original, 1:1, 4:5, 5:7, 2:3, 16:9 and Custom, with a lock; **X** swaps portrait and landscape; **O** cycles thirds, grid, golden ratio and diagonals while cropping; **Enter** applies, **Esc** cancels; a Reset.
4. **Straighten:** an Angle slider (−45…+45°, 0.01° steps; the crop shrinks to stay inside the photo) and a level line drawn along the horizon or a wall (the **Level** button, or **Ctrl-drag** while cropping, as in LightCraft (and, from general knowledge, Lightroom; not checked here)). **Rotate left/right** (Ctrl+[ / Ctrl+]) and **flip** horizontal/vertical. Auto straighten comes later with Upright.

### Process versions

| Behaviour | Detail | Source |
|---|---|---|
| What is stored | `process` in the develop settings (`engine/develop/settings.ts`), saved in the catalog, the history and the `lightbench:Develop` sidecar field. It is separate from the settings' existing `version: 1`, which numbers the JSON layout (the schema) and stays as it was. | Owner's decision; design LightBench's |
| Old and new edits | A saved edit without `process` (everything saved before 0.3.0) reads as version 1. New edits, unedited photos and **Reset all** get the current version. A malformed value reads as 1. | Owner's decision |
| What a version covers | Everything that turns the same settings into different pixels: the RAW stage (white level choice, highlight reconstruction, demosaic), colour (camera matrix, white balance maths), the slider mappings (Exposure, the Contrast → sigmoid mapping, the tone-equalizer bands behind Highlights/Shadows/Whites/Blacks, Vibrance/Saturation), the display transform, and the geometry stage (crop rounding and the warp kernel). | Branching on it | Each version has its own parameter set (`processParams(version)`): today the tone range, the tone-equalizer band weights and the contrast spread, moved out of fixed constants. `displayUniforms` and `toneBands` read them from the photo's version. A future version adds an entry; version 1's entry never changes. | LightBench |
| Shown | At the foot of the tool stack: “Process version 1 (current)”. An older edit also shows, above the groups, “This photo was edited with process version N” and **Update to current process**, which records one history step “Update to process M”: the step before it shows the old rendering, Ctrl+Z goes back. An edit from a newer LightBench says so and is shown with the newest version this build knows, never rewritten. | Lightroom's process version and its update prompt (from general knowledge of Lightroom; not checked in Lightroom here) |
| Copy/paste | **Process version** is an item of the paste checklist's Advanced group (unticked by default, like the rest of that group). | Lightroom's Copy Settings lists Process Version (not checked here) |
| Testing an update | Only one rendering exists, so no real edit is older than current. On the development server, `?simulateProcess=2` adds a copy of version 1 as version 2 so the offer can be tried; production builds leave it out (`import.meta.env.DEV`). | Test scaffolding |

### The geometry stage and where the crop is used

| Behaviour | Detail | Source |
|---|---|---|
| One resample | Lens correction → rotate and perspective (straighten; later Upright) → flip (camera orientation + the user's turns and flips) → crop, darktable's pixelpipe order, are combined into one projective map from output pixels to the sensor (`engine/develop/geometry.ts`, `resolveGeometry`). Lens correction and perspective are identity for now and join the same map later, so a photo is resampled once whatever tools are used. | darktable `src/common/iop_order.c` (v5.0 order: lens 13, ashift 15, flip 16, crop 24.5); combining them is LightBench's choice (darktable's modules each resample) |
| Interpolation | With a straighten angle, the scene is warped once with bicubic interpolation (Catmull-Rom, a = −0.5) into a cached texture with its own mip chain (`engine/gpu/warp.wgsl`). Without an angle the map is whole-pixel (orientation, turns, flips, crop) and the scene is read directly: nothing is resampled. | darktable's default warp interpolator is bicubic: `plugins/lighttable/export/pixel_interpolator_warp` defaults to `bicubic` (`data/darktableconfig.xml.in`) and `DT_INTERPOLATION_DEFAULT_WARP = DT_INTERPOLATION_BICUBIC` (`src/common/interpolation.h`); its `_maketaps_bicubic` is the a = −0.5 cubic (`src/common/interpolation.c`) |
| Cache | The last warped scene is kept per scene and map: exposure, tone and colour sliders, Auto, the histogram, thumbnails and exports reuse it. Before/after and the eyes (which show no geometry) don't evict it. A new RAW stage (white balance, highlight reconstruction, demosaic) or another photo drops it. | LightCraft review (“cache the warped result”) |
| Crop coordinates | Normalised (0…1) in the straightened frame: the photo after every geometry correction except the crop, in its final orientation. So crops (and later masks) stay on the same content when lens or Upright settings change. | Owner's requirement; LightCraft's model |
| Whole pixels | The crop is rounded inwards to whole pixels, so a turned crop never reads outside the photo. A locked aspect gets the whole-pixel size nearest to it (a 1:1 crop is exactly square). A crop found outside the turned photo (e.g. pasted where the photo's size wasn't known) is pulled inside before rendering. | LightBench |
| Everywhere | Develop's view, the histogram and clipping, **Auto** (it measures the cropped frame), Export (`renderOutput`: the crop at 100 %, then resized), thumbnails (`renderThumbnail`), the culling/Compare/Survey 100 % renders (`FullRenderer`), the background developer (Paste, Sync, Auto Sync, presets, develop new photos) and virtual copies all render through the same map, because the geometry travels in `displayUniforms`. The white balance picker and the sensor-clipping overlay map through it too. | Owner's requirement |
| Old edits | An edit without geometry renders exactly as before: the map is built in uv units from 0, 1 and −1 entries and equals the old orientation map (unit test), and the full-size export of a 0.2.0 edit is bit-identical (below). | Owner's requirement |

**Limitations:**
- The fitted views of the Library loupe and culling still show the camera's embedded preview, which ignores all edits (as before), so a crop appears there only at 100 % and in thumbnails.
- While straightening outside the crop tool (the Angle slider), every slider step warps the photo again at full resolution: expected to be quick on a real GPU (not measured on the owner's GPU yet) and visibly slower on the software GPU used for testing (not measured). Inside the crop tool the photo is drawn directly and nothing is warped until the crop is applied.
- The warped copy is a second full-resolution texture (8 bytes per pixel: about 190 MB for a 24 MP crop, plus a third more for its mips) while a straightened photo is open.
- At the very corners of a maximal straightened crop, the bicubic taps reach up to two pixels past the photo's edge and repeat the edge pixels (darktable's interpolation does the same).

## Part 2: Lens corrections

**What it does.** Corrects the lens's distortion, transverse chromatic aberration (TCA, the red and blue fringes towards the corners) and vignetting (dark corners). The data comes from the camera's own corrections when the RAW file carries them, otherwise from the Lensfun database, exactly as darktable's lens module offers them (`src/iop/lens.cc`: methods "embedded metadata" and "Lensfun database"). The correction is one more step of the single geometry resample from Part 1. A **Lens** section in the Crop & Lens group shows which data corrected the photo and with which lens, lets you pick another Lensfun camera or lens when the match is wrong, and has Lightroom-style **Distortion** and **Vignetting** amounts and a **Remove chromatic aberration** switch.

Owner's choices (2026-10-12):
1. **Data source order:** the camera's own corrections first, otherwise Lensfun (darktable's `reload_defaults` prefers the embedded data when the file has some).
2. **Lensfun database:** LightBench's own pinned copy, served with the app but not part of the install; downloaded the first time a photo needs it, then kept for offline use.
3. **On by default when a profile is found, but existing edits don't change:** an edit saved before this part keeps lens correction off and renders byte-identically; new photos and edits get Auto. One checkbox turns it off (or on, for an older edit).
4. **Show the source** (camera or Lensfun, and the lens/profile name), let the user pick another Lensfun camera or lens, and offer Distortion and Vignetting amounts and a chromatic aberration switch.

## Part 3: Transform and Upright

**What it does.** A **Transform** section in the Crop group corrects perspective: leaning buildings, walls seen at an angle and tilted horizons. **Upright** does it in one click (Auto, Level, Vertical, Full) or from lines drawn on the photo (Guided); Lightroom's **Transform sliders** adjust it by hand. The crop group's Straighten controls get an **Auto** button that levels the photo along the lines it finds. The engine is darktable's "rotate and perspective" module (ashift): its line detector, its choice and weighting of lines, its fit with the photo's own focal length, and its automatic crop; LightCraft's guards keep it from "correcting" trees, roads and other scene structure.

Owner's choices (2026-10-12):
1. **All four Upright ways:** Auto (level and verticals in one click), Level, Vertical and Full as separate one-click fixes, Guided (draw 2–4 lines), and the Manual sliders (Vertical, Horizontal, Rotate, Aspect, Scale, X/Y Offset).
2. **Auto straighten** in the crop group, sharing the line detector, setting the existing straighten Angle.
3. **darktable's ashift as the engine**, translated to TypeScript, with the photo's real focal length and crop factor; **LightCraft's guards** against false corrections; the **solved correction stored in the edit**; Auto re-detected per photo when pasted, Manual values copied; no empty corners after the transform; existing edits unchanged.

## Part 5: Phone DNGs (linear DNG) and Fujifilm X-Trans

**What it does.** The two RAW layouts LightBench used to refuse now open, develop, thumbnail and export like any other RAW:
- **Linear DNGs** (Apple ProRAW, many phone DNGs, the linear output of DNG converters): three colours per pixel, already demosaiced, but still scene-linear camera RGB. They go through the RAW steps (black and white levels, white balance, highlight reconstruction, the camera matrix) without a demosaic, not through the JPEG path. Their colour comes from the file's own DNG colour model: the two calibration matrices interpolated for the photo's white balance.
- **Fujifilm X-Trans RAFs**: darktable's default X-Trans demosaic, **Markesteijn 1-pass**, translated to WebGPU, with the raw steps and the clipping indicators taught the 6×6 pattern.
- **Bayer DNGs that LibRaw has no colour matrix for** (e.g. Google Pixel phone DNGs) used to fail with “Matrix is not invertible”; they now use the DNG colour model too.

Old edits of Bayer photos render byte-identically (below). ProRAW's embedded semantic masks (sky, person, skin, hair mattes) are a follow-up for the Phase 4 masks, not built here.

## Part 7: Lightroom's crop, straighten, orientation, Transform and Upright in sidecars

**What it does.** LightBench now reads and writes Lightroom's own crop, straighten angle, rotate/flip, Upright mode and Transform sliders in `.xmp` sidecars. A crop made in Lightroom appears in LightBench, and a crop changed in LightBench appears in Lightroom. Where the two models differ, LightBench takes the closest match and says so: an Upright mode read from Lightroom is solved again by LightBench's own Upright, and the Transform section says the result may differ slightly from Lightroom's. Nothing renders differently, so the process version stays 1.

Owner's choices (2026-10-12):
1. **Both directions:** read them and write them.
2. **Closest match, said so.** A Lightroom Upright is re-run with LightBench's Upright, with a note in the Transform section.

### The fields and their convention

| Behaviour | Detail | Source |
|---|---|---|
| Fields read and written | `crs:HasCrop`, `crs:CropLeft/Top/Right/Bottom`, `crs:CropAngle`, `tiff:Orientation`, `crs:PerspectiveUpright` and `crs:PerspectiveVertical/Horizontal/Rotate/Scale/Aspect/X/Y`. No other `crs:` field is written. | Field names: ExifTool `lib/Image/ExifTool/XMP.pm` (its `crs` table, fetched from ExifTool's GitHub repository); LightCraft `crates/engine/src/crs.rs` lines 416–449 |

| Crop edges | The edges are the crop rectangle's top-left corner (`CropLeft`, `CropTop`) and bottom-right corner (`CropRight`, `CropBottom`) **on the photo as stored**, before `tiff:Orientation` and before straightening, normalised to its width and height. The rectangle is turned by `CropAngle` about the photo's centre, in pixels. LightBench's crop (normalised in the straightened, oriented frame, Part 1) is converted to and from this (`sidecar/lightroom.ts`). | darktable `src/develop/lightroom.c` (commit `6271f53`): reads the edges (lines 492–501), turns both corners about the centre in pixels of `tiff:ImageWidth × ImageLength` (lines 1343–1361), then applies the stored → shown orientation to them (lines 1363–1372). | CropAngle's sign | **LightBench's angle = −CropAngle**, reversed once more for a mirrored orientation (2, 4, 5, 7): angle = −CropAngle × det(orientation). | darktable negates it (`data->pc.angle = -…`, line 501) and negates it again for mirrored orientations (lines 1374–1379). | HasCrop | The edges count only when `HasCrop` is True. `HasCrop="False"` means uncropped, angle 0. | tiff:Orientation | Lightroom keeps its Rotate and Flip in the photo's orientation (EXIF codes 1–8), not in the crop. LightBench's turns and flips sit on top of the camera's orientation, so they are read as the sidecar's orientation × the inverse of the file's own, and written back as the total. | CropConstrainToWarp | ExifTool lists it among the fields Lightroom 3 added with its manual lens-correction sliders (PerspectiveVertical, Horizontal, Rotate, Scale). | crs:AlreadyApplied | True means the pixels already contain these settings, as in an exported file. LightBench reads no geometry from such a packet and writes none into it. | ExifTool (“written by LightRoom beta 4.1”); LightCraft skips such packets (`crs.rs` line 100) |
| Upright modes | `PerspectiveUpright` 0 Off, 1 Auto, **2 Full, 3 Level, 4 Vertical**, 5 Guided. | ExifTool (`XMP.pm`, PerspectiveUpright, citing its forum thread 14012, each code annotated with Lightroom's tooltip). | Transform sliders | They map number for number (both −100…100; Rotate ±10°; Scale in %; the offsets). ### Writing

| Behaviour | Detail | Source |
|---|---|---|
| Only into Camera Raw sidecars | The fields are written only into a sidecar that already has Lightroom or Camera Raw settings (`crs:ProcessVersion`), and never into an already-applied one. The crop convention rests on darktable's importer and LightCraft's catalog importer (checked by its authors against 223 exported crops); the Upright codes on ExifTool (LightCraft's differing table is not used); the slider signs on LightCraft's description of Lightroom. How Lightroom treats a mode LightBench wrote while Lightroom's own `UprightTransform_*` matrices are still in the file (re-analysis, or reuse of the matrix for that mode) is unknown.
- LightBench writes Lightroom's fields only into sidecars that already hold Camera Raw settings, so a photo edited only in LightBench shows no crop in Lightroom. Writing into other sidecars would need checking how Lightroom treats `crs:` fields without `crs:ProcessVersion`.
- Lightroom's Upright is solved again by LightBench (darktable's model), so the correction differs somewhat; Guided lines aren't imported; the Transform sliders' strength differs per step.
- With lens correction or a transform, LightBench's crop frame (lens-corrected and fitted, Part 1 and Part 3) and Lightroom's aren't the same picture, so the crop lands on approximately the same content.
- `CropConstrainToWarp`'s meaning (Constrain Crop) is inferred from ExifTool's grouping; `CropWidth/Height/Units` aren't touched.
- The stored size comes from the catalog. For a JPEG whose EXIF has an orientation but no pixel dimensions, the catalog may hold the turned size, which would turn a straightened Lightroom crop slightly wrongly; JPEGs with mirrored EXIF orientations are read as unmirrored, as before.
- As before this part, LightBench's sidecar writer re-serializes the file: names, values and element content are kept, but whitespace inside start tags and around the packet wrapper isn't.
- A photo whose Lightroom geometry was read but whose edit wasn't written yet (the folder waiting for write permission), and whose crop is then removed in LightBench, keeps Lightroom's crop in the sidecar until the crop is changed again.
