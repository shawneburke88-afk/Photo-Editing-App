# Phase 3 — Editing depth

See [PLAN.md](PLAN.md#phase-3--editing-depth) for the whole phase and [USABILITY.md](USABILITY.md) for the decisions behind it. Phase 3 adds darktable's editing tools behind Lightroom-style controls. It starts with the groundwork they need: process versions, so that rendering changes never alter existing edits, and the Develop tool stack that the new tools join, with Crop as its first group.

## Part 1: Process versions, the tool stack, and Crop

**What it does.** Three things. Every edit now records which version of LightBench's rendering it uses (its **process version**), so later rendering changes never silently change an existing edit. Develop's right panel is now **one scrolling stack of tool groups** in workflow order with a **jump bar**. Its new first group is **Crop**: crop, straighten, rotate 90° and flip, on the photo and in the panel, Lightroom-style.

Owner's choices (2026-10-12):
1. **Process versions first.** Existing edits are version 1 (today's rendering); new edits get the current version; rendering code can branch on the version; the version is shown unobtrusively and an older edit offers **Update to current process**, which can be compared and undone through the history. Today there is one rendering, so this is the mechanism and its tests.
2. **The tool stack**, already decided after round 2: one scrolling stack, Crop & Lens first, then Basic; collapsible groups; a jump bar with icons and one-word labels (labels hide when narrow, the name shows on hover). Only groups with content exist (Crop, Basic); Curve, Colour, Detail and Effects slot in later. The on/off **eye** per group (an idea from LightCraft; LightBench's choice to include it) shows the photo without that group.
3. **Crop, Lightroom-style:** **R** opens it on the photo (an action in the shortcut registry, so it can be changed); drag corners or edges to resize, inside to move, outside to turn; the crop box stays level and the photo turns under it (Lightroom's way; LightCraft turns the box instead). Aspects Original, 1:1, 4:5, 5:7, 2:3, 16:9 and Custom, with a lock; **X** swaps portrait and landscape; **O** cycles thirds, grid, golden ratio and diagonals while cropping; **Enter** applies, **Esc** cancels; a Reset.
4. **Straighten:** an Angle slider (−45…+45°, 0.01° steps; the crop shrinks to stay inside the photo) and a level line drawn along the horizon or a wall (the **Level** button, or **Ctrl-drag** while cropping, as in LightCraft (and, from general knowledge, Lightroom; not checked here)). **Rotate left/right** (Ctrl+[ / Ctrl+]) and **flip** horizontal/vertical. Auto straighten comes later with Upright.

### The geometry stage and where the crop is used

| Behaviour | Detail | Source |
|---|---|---|
| One resample | Lens correction → rotate and perspective (straighten; later Upright) → flip (camera orientation + the user's turns and flips) → crop, darktable's pixelpipe order, are combined into one projective map from output pixels to the sensor (`engine/develop/geometry.ts`, `resolveGeometry`). Lens correction and perspective are identity for now and join the same map later, so a photo is resampled once whatever tools are used. | darktable `src/common/iop_order.c` (v5.0 order: lens 13, ashift 15, flip 16, crop 24.5); combining them is LightBench's choice (darktable's modules each resample) |
| Interpolation | With a straighten angle, the scene is warped once with bicubic interpolation (Catmull-Rom, a = −0.5) into a cached texture with its own mip chain (`engine/gpu/warp.wgsl`). Without an angle the map is whole-pixel (orientation, turns, flips, crop) and the scene is read directly: nothing is resampled. | darktable's default warp interpolator is bicubic: `plugins/lighttable/export/pixel_interpolator_warp` defaults to `bicubic` (`data/darktableconfig.xml.in`) and `DT_INTERPOLATION_DEFAULT_WARP = DT_INTERPOLATION_BICUBIC` (`src/common/interpolation.h`); its `_maketaps_bicubic` is the a = −0.5 cubic (`src/common/interpolation.c`) |
| Cache | The last warped scene is kept per scene and map: exposure, tone and colour sliders, Auto, the histogram, thumbnails and exports reuse it. Before/after and the eyes (which show no geometry) don't evict it. A new RAW stage (white balance, highlight reconstruction, demosaic) or another photo drops it. | LightCraft review (“cache the warped result”) |
| Crop coordinates | Normalised (0…1) in the straightened frame: the photo after every geometry correction except the crop, in its final orientation. So crops (and later masks) stay on the same content when lens or Upright settings change. | Owner's requirement; LightCraft's model |
| Whole pixels | The crop is rounded inwards to whole pixels, so a turned crop never reads outside the photo. A locked aspect gets the whole-pixel size nearest to it (a 1:1 crop is exactly square). A crop found outside the turned photo (e.g. pasted where the photo's size wasn't known) is pulled inside before rendering. | LightBench |
| Everywhere | Develop's view, the histogram and clipping, **Auto** (it measures the cropped frame), Export (`renderOutput`: the crop at 100 %, then resized), thumbnails (`renderThumbnail`), the culling/Compare/Survey 100 % renders (`FullRenderer`), the background developer (Paste, Sync, Auto Sync, presets, develop new photos) and virtual copies all render through the same map, because the geometry travels in `displayUniforms`. The white balance picker and the sensor-clipping overlay map through it too. | Owner's requirement |
| Old edits | An edit without geometry renders exactly as before: the map is built in uv units from 0, 1 and −1 entries and equals the old orientation map (unit test), and the full-size export of a 0.2.0 edit is bit-identical (below). | Owner's requirement |

**Limitations:**
- The fitted views of the Library loupe and culling still show the camera's embedded preview, which ignores all edits (as before), so a crop appears there only at 100 % and in thumbnails.
- While straightening outside the crop tool (the Angle slider), every slider step warps the photo again at full resolution: expected to be quick on a real GPU (not measured on the owner's GPU yet) and visibly slower on the software GPU used for testing (not measured). Inside the crop tool the photo is drawn directly and nothing is warped until the crop is applied.
- The warped copy is a second full-resolution texture (8 bytes per pixel: about 190 MB for a 24 MP crop, plus a third more for its mips) while a straightened photo is open.
- At the very corners of a maximal straightened crop, the bicubic taps reach up to two pixels past the photo's edge and repeat the edge pixels (darktable's interpolation does the same).
- Lightroom's `crs:Crop*` sidecar fields aren't written or read, so Lightroom and darktable don't see LightBench's crop. Auto straighten comes with Upright.
- The Lightroom behaviours quoted (R, X, O in the crop tool, Ctrl-drag to straighten, the copy default, process version updates) are from general knowledge and the owner's description, not checked in Lightroom or against Adobe's pages here.

## Part 3: Transform and Upright

**What it does.** A **Transform** section in the Crop group corrects perspective: leaning buildings, walls seen at an angle and tilted horizons. **Upright** does it in one click (Auto, Level, Vertical, Full) or from lines drawn on the photo (Guided); Lightroom's **Transform sliders** adjust it by hand. The crop group's Straighten controls get an **Auto** button that levels the photo along the lines it finds. The engine is darktable's "rotate and perspective" module (ashift): its line detector, its choice and weighting of lines, its fit with the photo's own focal length, and its automatic crop; LightCraft's guards keep it from "correcting" trees, roads and other scene structure.

Owner's choices (2026-10-12):
1. **All four Upright ways:** Auto (level and verticals in one click), Level, Vertical and Full as separate one-click fixes, Guided (draw 2–4 lines), and the Manual sliders (Vertical, Horizontal, Rotate, Aspect, Scale, X/Y Offset).
2. **Auto straighten** in the crop group, sharing the line detector, setting the existing straighten Angle.
3. **darktable's ashift as the engine**, translated to TypeScript, with the photo's real focal length and crop factor; **LightCraft's guards** against false corrections; the **solved correction stored in the edit**; Auto re-detected per photo when pasted, Manual values copied; no empty corners after the transform; existing edits unchanged.

### Line detection, the fit and the guards

| Behaviour | Detail | Source |
|---|---|---|
| Detector | LSD 1.6 (Grompone von Gioi et al.) with darktable's parameters: scale 0.99, sigma 0.6, quantisation 2, angle tolerance 22.5°, log ε 0, density 0.7, 1024 bins. Input: grey = 0.3 R + 0.59 G + 0.11 B of the scene-linear photo raised to 0.45, × 256. Runs in a worker. | darktable `ashift_lsd.c`, `line_detect`, `rgb2grey256`, `gamma_correct`; darktable applies the gamma to RAW input only, LightBench to JPEGs too because its JPEGs are scene-linear as well |
| Input image | The photo before the perspective, at most 1600 px on its long edge (a level of the scene's mip chain, so nothing is rendered for it), detected once per photo. **When lens correction exists**, it must be the lens-corrected photo, as darktable's ashift sits after `lens`: `DevelopEngine.analysisImage` is the one place to change (its comment says how). | darktable's pipe order; the 1600 px limit is LightBench's |
| Line selection | Lines along the image border dropped; weight = length × width × precision; within 30° of vertical or horizontal and longer than 5 px; then darktable's RANSAC keeps the lines meeting in one vanishing point per direction (self-tuning ε, 400 runs, full permutations for ≤ 5 lines; vanishing points inside the photo rejected). | darktable `line_detect`, `ransac`, `_remove_outliers`; a seeded generator replaces C's `rand()` so a photo always gives the same result |
| Model and fit | darktable's `_homography` (rotation, shear, vertical and horizontal lens shift with their compression, aspect) and Nelder-Mead fit of `model_fitness` (400 iterations, ε 10⁻³; parameters through darktable's logit with its “soft” ranges ±180°, ±2, ±0.5). Fits that more than quadruple the image area are refused (`NMS_INSANE`). | darktable `_homography`, `model_fitness`, `nmsfit`, `ashift_nmsimplex.c` (Michael F. Hutt, MIT) |
| Focal length | The EXIF focal length × crop factor (35 mm FocalLengthIn35mmFilm / focal length, or 1), as darktable's `reload_defaults` reads them, used with ashift's “specific” lens model and its default lens dependence of 100 %. 28 mm when the file has none. Stored with the correction. | darktable `reload_defaults`, `DEFAULT_F_LENGTH`; darktable's own default is the “generic” model (28 mm, no lens dependence); the owner asked for the real focal length |
| Units | Detection, fit and rendering all use pixels of the full-size photo in its sensor orientation. darktable fits on its preview buffer's size while its lines are scaled to full size (`nmsfit`: `fit.width = g->lines_in_width`); LightBench keeps one size so the result renders as fitted. | Reading of `nmsfit` (not run in darktable here) |
| Guards | A family's vanishing point counts only with at least 3 inlier lines, a total inlier length of ¼ of the long edge, inliers spread across ⅕ of it, 60 % of the family's length agreeing, and a vanishing point at least one long edge away from the photo's centre (closer, it is a road or sun rays, not camera tilt). Level and Auto straighten need half of the lines' length to agree within 2° (else “The lines found don’t agree on a level”). Fewer than 2 lines: “Not enough straight lines were found to correct this photo.” | LightCraft `reliable`, `level_angle`; darktable `MINIMUM_FITLINES` = 2 |
| Guided | Draw 2–4 lines on the photo (Shift+T or the Guided button). The photo is shown whole, corrected, with the part beyond its frame dimmed; drag a line's ends to adjust it, click it and press Delete (or double-click it) to remove it, Esc or Enter to finish. Two or more lines closer to vertical fix the verticals (`ASHIFT_FIT_VERTICALLY`), two or more horizontal ones the horizontals (`ASHIFT_FIT_HORIZONTALLY`), both kinds everything with shear; with fewer, the photo stays uncorrected and the hint says “Draw one more line in the same direction.” Lines are darktable's drawn lines (weight 1, type from their direction). While a line is drawn or dragged the photo doesn't move; it is solved again on release. Each add, move and removal is a history step. | darktable's drawn-lines method (`_draw_basic_line`, `_draw_retrieve_line_type`, `MINIMUM_FITLINES`); four lines at most is Lightroom's as the owner described it; the on-photo behaviour is LightBench's |

### Transform sliders

| Slider | Range | What it does (darktable parameter) |
|---|---|---|
| Vertical | −100…100 | ashift's vertical lens shift (±100 = ±1, darktable's `LENSSHIFT_RANGE`); + widens the top |
| Horizontal | −100…100 | horizontal lens shift; + narrows the right side |
| Rotate | −10…10° | ashift's rotation (`ROTATION_RANGE` 10); + turns clockwise |
| Aspect | −100…100 | ashift's aspect adjust, 2^(value/100) (darktable's 0.5…2 range); + wider |
| Scale | 100…150 % | zooms into the fitted photo (100 % = largest without empty corners) |
| X / Y Offset | −100…100 | moves the photo inside its frame (±100 = a quarter of the photo); the frame shrinks where needed. X + moves it right, Y + up |

The sliders add to what Upright solved (they are stored apart, as in Lightroom). Directions, the Scale range and the offset scale are LightBench's choices (Lightroom's own ranges and directions are from general knowledge, not checked). Each slider has the usual hint and tooltip.

### Stored transform, geometry and the crop

| Behaviour | Detail | Source |
|---|---|---|
| What is stored | `geometry.transform` in the develop settings (catalog, history, `lightbench:Develop` sidecar): the Upright mode, **the solved correction** (darktable's rotation, lens shifts and shear), the guides, the slider values and the focal length used. Rendering uses these numbers and never detects lines again, so Develop, Export, thumbnails, the 100 % renderer, the background developer and virtual copies render the same. An edit without it has no transform. | Owner's requirement; LightCraft stores its homography (`Geometry::upright_transform`); darktable stores the fitted parameters |
| Where it sits | Lens correction → **perspective** → straighten → flip → crop (darktable: `lens` → `ashift` → `flip` → `crop`). The perspective is the 3×3 map `perspectiveMap` inserted into `resolveGeometry`'s single map, before straightening, in the sensor's orientation as in darktable, so it stays on the content when the photo is turned or flipped. | darktable `iop_order.c`; Part 1's geometry pass |
| Screen terms | Settings are stored as seen on screen (Vertical is vertical on screen, whatever the camera's orientation) and converted to the sensor's axes when rendering. Rotate and flip convert them too (`turnTransform`), so the correction stays on the content; a unit test checks the map is unchanged for every orientation and turn. | darktable relabels its sliders for sideways photos (`isflipped`); storing screen terms is LightBench's choice, so pasting between differently oriented photos means the same thing |
| No empty corners | The corrected photo is fitted into its frame (the photo's own size) with darktable's automatic crop in “original format” mode: the largest rectangle of the photo's shape inside the corrected outline, its centre found by Nelder-Mead (`do_crop`, `crop_fitness`, `ASHIFT_CROP_ASPECT`). Scale and the offsets act on that fit. So the frame never shows empty areas, and the crop (stored in that frame, as in Part 1) stays inside it. Lightroom's Constrain Crop checkbox is not offered: it is always on (showing empty areas would need the warp to paint outside the photo). | darktable ashift (crop mode verified in `ashift.c`); always on is LightBench's choice |
| Resample | A transform makes the map non-exact: the photo is warped once (bicubic) and cached, as with a straighten angle. The crop tool's view shows the corrected photo directly. | Part 1 |
| Crop eye | The Crop group's eye now also hides the transform. | LightBench |
| Process version | Unchanged (still 1): a new tool that is off by default needs no new version (the rule in `process.ts`). A later change to the transform's maths would. | Part 1's rule |

**Limitations:**
- The test photos have few strong verticals: philadelphia.nef is mostly trees and a fountain, so Upright's vertical correction was checked on synthetic photos and Guided lines, not on a real building. Behaviour on the owner's own architecture photos is not verified.
- Lightroom's Upright, Transform and Guided behaviours and keys quoted here are from general knowledge and the owner's description, not checked in Lightroom.
- Constrain Crop is always on; Lightroom's option to see the empty areas is not offered.
- Lightroom's `crs:Perspective*` and `crs:Upright*` sidecar fields are not read or written; LightBench's transform lives in `lightbench:Develop`.
- Each Transform slider step warps the photo again at full resolution (as the Angle slider does, Part 1); quick on a real GPU is expected, not measured on the owner's GPU.
- Line detection runs on the CPU in a worker: about 0.3 s for a 900 × 600 synthetic image in Node (unit test probe); in the browser it was not timed separately.
- LSD is AGPL-3.0-or-later (see THIRD_PARTY_NOTICES.md): its source-offer terms apply to the web app; the repository is public but the app has no link to it yet (the owner's decision).
- The line-detection image will need the lens-corrected photo once lens correction exists (see “Input image”).
